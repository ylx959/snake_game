# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Server-authoritative snake. A C++ game server owns every rule and runs the
clock; the browser draws the state it is sent and forwards key presses.

## Commands

```bash
# game-server
cd game-server
./dev.sh                                  # watch + rebuild + restart on change
cmake -S . -B build                       # first time, or after editing CMakeLists.txt
cmake --build build
ctest --test-dir build --output-on-failure
./build/core_tests "[command]"            # one tag group; see below
./build/game-server                       # ws://127.0.0.1:8000/ws ; PORT=9000 to move it

# web
cd web
npm run dev                               # http://127.0.0.1:3000, Fast Refresh
npm run typecheck                         # tsc --noEmit
npm run lint                              # eslint . (next lint was removed in Next 16)
npm run build && npm start                # production check
```

`core_tests` is Catch2. Every case is tagged, and `catch_discover_tests`
registers each one with CTest individually:

```bash
./build/core_tests "[command]"          # one tag group
./build/core_tests "Absent food serializes as null"
ctest --test-dir build -R tail          # by name, via CTest
```

Tags: `[snake]` `[collision]` `[game]` `[wire]` `[command]`.

Both servers must be running to use the app. The game server binds **loopback
only**, so use `127.0.0.1`, not `localhost` — on macOS `localhost` may resolve
to `::1` first and fail.

## Environment notes

- **Do not remove `allowedDevOrigins` from `web/next.config.ts`.** `next dev`
  rejects dev-only endpoints — including the HMR WebSocket — for any request
  carrying an Origin it was not started with, and browsers always send Origin.
  Without that setting the HMR upgrade returns 400, the dev client never finishes
  booting, and every page renders from SSR but **never hydrates**: effects never
  run, the board stays blank, the status sticks on "connecting", and there is no
  console or build error of any kind. It reproduces on a trivial page and under
  both Turbopack and `--webpack`, so it looks like broken app code and is not.
- `web/AGENTS.md` and `web/CLAUDE.md` are regenerated by `next dev` and are
  gitignored. They are not hand-written project docs.

## Architecture

### The wire contract is written twice

`Game::toJson()` in `game-server/src/Game.cpp` and `web/types/game.ts` describe
the same message. **Change both in the same commit.** There is no schema and no
codegen. The `[wire]` tests pin the serialized shape on the C++ side, so they
catch a field that is renamed or dropped — but nothing checks that
`types/game.ts` agrees, so a field added on one side alone still slips through.

The server pushes `{"type":"state", ...}` every tick; the client sends
`{"type":"turn"|"start"|"pause"|"reset"}`. The client never computes game state.

### Why the split matters

The server runs the clock, so a client cannot move faster by sending more
messages, and every rule is testable without a socket. If you find yourself
adding game logic to the browser, it belongs in `Game`/`Snake`/`Collision`.

### game-server

Dependencies are fetched by CMake at configure time (`FetchContent`, release
archives pinned by SHA256 — no system packages, no git clones):

- **nlohmann/json** — used by `Game::toJson()` and `parseCommand()`. `PRIVATE`
  to `snake_core` because no public header exposes it; `core_tests` links it
  separately to assert on the serialized format.
- **Catch2 v3** — the test framework.

`WebSocketServer.cpp` is still hand-written RFC 6455 on POSIX sockets, including
inline SHA-1 and base64 for the handshake. That is the one piece with no library
behind it, and replacing it is a live option, not a violation of anything.

There is **no rule against dependencies here** — take one where it pays for
itself.

- `WebSocketServer` is transport only and knows nothing about snake. It accepts,
  upgrades, and runs a callback on a detached thread per connection. It also
  answers `GET /health` for non-upgrade requests.
- `main.cpp` wires one `Game` per connection: a ticker thread advances state and
  pushes it, the main thread pumps commands. `gameMutex` guards the `Game`; a
  `condition_variable` (not a sleep) paces the ticker so a disconnect ends it at
  once instead of one tick later. Commands are parsed *outside* the lock.
- `Command` owns the client half of the protocol. `parseCommand()` is a pure
  function from text to a value, so it is tested without a `Game`, a socket, or
  a thread; `apply()` is the only part with a side effect. Parsing is
  non-throwing (`allow_exceptions=false`) because malformed text off a socket is
  an expected case, not an exceptional one — every rejection returns `nullopt`.

Three rules in `Game`/`Snake` are load-bearing and easy to break:

- `Game::tick()` resolves food **before** `snake_.move()`. That is what makes
  growth and score land on the same tick and keeps the tail in place so the new
  segment appears immediately.
- `hitsSelf()` excludes the last body cell. The tail vacates on the tick the head
  arrives, so following your own tail is legal.
- `Snake` buffers a turn in `pending_` and only commits it in `move()`, and
  `turn()` compares against the committed `direction_`. This is what stops two
  key presses inside one tick from folding the snake onto its own neck.

### web

Layered so that only one file knows about both React and the socket:

- `lib/` (`websocket.ts`, `input.ts`, `renderer.ts`) imports no React.
  `Renderer` is stateless with respect to the game — it draws exactly the state
  it is handed, so it cannot disagree with the server.
- `hooks/useSnakeGame.ts` is the only React↔socket seam: socket lifecycle,
  server state mirrored into React state, keyboard binding.
- `components/game/` is presentational. `ScoreBoard` shows connection status
  instead of game status while the socket is not open, because that is the thing
  the player can act on.

The `@/*` path alias maps to the **web root**, not `src/` — there is no `src/`.

The backend URL comes from `NEXT_PUBLIC_WS_URL` (`web/.env.local`), falling back
to `ws://127.0.0.1:8000/ws`.
